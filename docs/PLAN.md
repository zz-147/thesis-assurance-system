# 现状盘点 + 目标架构 + 2 周计划

- 项目：**tas（thesis-format-assistant）** — 毕业论文（设计）格式统一工具
- 版本：v1.0（2026-10-26：功能补齐，测试/评测/Web/批量全部完成）
- 依据：`D:\zdsh\work\thesis-format\writing_standard_clean.txt`（商丘学院应用科技学院《毕业论文（设计）撰写规范（修订）》，128 行）
- 规则表：[../rules/rules.json](../rules/rules.json)（38 条：P0 23 / P1 15）
- 定位：检查器（教师端诊断）→ 修复引擎（学生端一键修复）→ 规范文档解析成规则集（教师端核心）→ Web 双入口 + 评测数字

## 0. 需求（v0.2，2026-10-24 晚确认）

**两个真实使用者，同一套规则引擎、两种输出：**

- **教师 / 助教**：上传一份**规范文档** → 解析成规则集 → 批量分析学生论文/文档是否符合规范 → 逐份问题清单 + 班级汇总。只诊断，不改学生文件。
- **学生**：上传自己的文档/论文 → 按规范（老师分享的或学院默认）检查 → 一键修复格式 → 下载新 docx + 修改说明。只改格式，不改内容。

```
规范文档 ──解析/LLM──> 规则候选 ──教师人审──> 规则集 profile
                                                    │
学生文档 ──解析──> 角色识别 ──> 规则检查 ──> 问题清单 ──> 教师端：报告 + 汇总
                                              └──> 学生端：修复（safe 项）+ diff + 复检
```

**对计划的影响**：①「规范文档 → 规则集」从"LLM 增强"升为**教师端核心功能（P0）**；②检查与修复共用同一规则集，教师端要诊断报告、学生端要修好的文件；③当前进度：检查器 v0.1 已跑通（22/23 条 P0、6 个测试通过），对 `out/` 9 份成品做首次体检发现 5 类系统性偏差（标题/摘要/目录段前距=0、正文 21–24 段左对齐）→ 说明检查器有效，也说明"成品"不是合规金标准。详见 [REQUIREMENTS.md](REQUIREMENTS.md)。

**2026-10-25 追加决策（v0.3）**

1. **每门学科规范可能不同** → 多 profile：[`profiles/index.json`](../profiles/index.json) 已建立（规则文件 + 学科体系 + 来源说明），`config.resolve_profile()` 支持按 id / 文件路径加载；新增学科 = 新增一个规则 JSON，不改代码。
2. **暂不做账号**：单机/校园内网；profile 先用 JSON 导出/分享，后续再接账号。
3. **真实性核验（教师端新增 P0）**：
   - 文献解析 + 元数据核验（Crossref/OpenAlex/arXiv 已确认可直连），结论分 `verified / likely / not_found / error`，**not_found 不等于造假**，必须附证据 URL 与"中文期刊可能未收录，需人工核实"提示；
   - 引用一致性（文内 [n] vs 文献表、越界/未引用/顺序/上标）纯离线可做；
   - 查重 / AIGC 检测不在本地做不可靠判断，预留外部报告接入口（P2）。
4. **文献不让学生改**：修复引擎白名单不含任何文献/文字操作；参考文献条目段落只读。
5. 并行开发：`fixer`（学生端修复）与 `tas.refs`（教师端文献核验）两条独立模块，Lead 负责 CLI 集成与验收。

## 2. 差距（做"产品/项目"还缺的 7 件事）

1. **没有"检查"能力**：现有代码只会"生成正确文档"，不会"诊断别人交上来的文档"。
2. **规则没有形式化**：规范是自然语言，规则散在一次脚本和硬编码路径里（部分脚本含 GBK 乱码路径，不可直接复用）。
3. **没有修复引擎**：对已有文档只会重新生成，缺少"保留内容、只改格式"的安全路径。
4. **没有评测**：8 份成品是自己生成的，不等于真实学生文档；没有标注集、没有误报率。
5. **「规范文档 → 规则集」没实现**：教师端核心链路（上传规范 → LLM 抽取规则候选 → 教师人审 → 检查学生文档）目前只能手写 rules.json —— 这也正是「AI 应用」叙事的落点。
6. **没有产品形态**：无 CLI / 报告 / 批量 / 界面；mockup 只是静态页。
7. **隐私红线**：`out/`、`work/` 下文档含真实姓名、学号、手机号，不能进公开仓库。

## 3. 目标架构

```
tas/
├─ pyproject.toml            # Python 3.12，依赖：python-docx、lxml（渲染预览另配）
├─ rules/
│  └─ rules.json             # 规则数据 v0.1（38 条）— 与代码分离
├─ src/tas/
│  ├─ cli.py                 # tas check / tas fix / tas batch / tas report
│  ├─ docx_io.py             # 读文档模型：sections/paragraphs/runs/tables + 样式继承解析
│  ├─ roles.py               # 段落角色识别：页面区/标题级/正文/题注/TOC/参考文献…
│  ├─ config.py              # profile（sci_eng | humanities）、规则筛选、容差
│  ├─ checkers/              # 每条规则一个函数，返回 Issue（定位+实际值+期望值）
│  ├─ fixer.py               # Issue → 修改指令 → 应用 → 生成新 docx + diff 清单
│  ├─ report.py              # issue 列表 → JSON / Markdown / HTML 报告
│  ├─ batch.py               # 目录批处理 + 汇总统计（老师端）
│  ├─ legacy.py              # .doc → .docx 适配（复用 doc_extract.py）
│  └─ llm/                   # LLM 层（只输出结构化 JSON 指令）
│     ├─ classify.py         # 结构识别兜底（标题级别、题注、参考文献条目）
│     ├─ spec_to_rules.py    # 规范文本 → 规则草案（人审后入库）
│     └─ explain.py          # "为什么不符合 + 怎么改" 的自然语言解释
├─ web/app.py                # Streamlit：上传 → 报告 → 一键修复 → 下载
├─ tests/                    # 单元测试 + 脱敏 fixtures
└─ eval/                     # 变异测试、指标报告
```

### 数据流

```
任意 .docx/.doc
   → 解析（docx_io：段落/表格/节/样式/编号/域）
   → 角色识别（roles.py：规则优先；不确定的段落交 LLM 只做"定级"）
   → 规则检查（checkers：每条规则 → Issue 列表）
   → 报告（JSON 为单一事实来源；Markdown / HTML / Web 只是渲染）
   → 修复（仅 safe 规则）→ 校验（重新跑检查）→ diff 预览 → 输出新 docx
   → 批量模式：目录级汇总（班级共性问题统计）
```

### 关键设计决策

1. **LLM 不直接改文档**：只输出 `{paragraph_id, action, params}` 结构化指令；由确定性代码执行并二次校验。
2. **检查与修复分离**：检查器先上线（零风险、可交付）；修复器必须 dry-run + diff + 可回滚。
3. **规则优先、LLM 兜底**：样式/编号/正则可判的绝不调模型（省钱、可复现、可测试）。
4. **规则数据与实现分离**：`rules.json` 可被老师/同学审阅，checker 函数按键索引。
5. **不碰文字内容**：需要改文字（如编号缺失、参考文献著录）的规则一律 `fixable=false`，只给建议。

## 6. 评测方案与指标（面试最值钱的部分）

### 数据三层

1. **已知良好集**：`out/` 8 份成品（自己生成的，只能证明"不误报"，不能证明"能修真实文档"）。
2. **变异集**：对好文档注入 N 类错误（每类 20 处），得 gold labels → 算检出率/误报率/定位准确率。
3. **真实问题集**：老师退回的版本、同学手写版本、`doc-templates` 里的 tpl/target 对照（脱敏后）。这才是"真实用户"证据。

### 指标

| 指标 | 定义 | 目标 |
|---|---|---|
| P0 规则检出率 | 变异注入的错误中被抓到的比例 | ≥ 95% |
| 误报率 | 好文档中被误报的段落/项比例 | ≤ 5% |
| 定位准确率 | Issue 给出的段落/表格定位正确比例 | ≥ 90% |
| 修复后通过率 | 修复后再检查，P0 规则通过比例 | ≥ 90% |
| 内容零改动 | 修复前后正文文本 hash 一致 | 100% |
| 单份耗时 | 检查 / 修复（10 页级文档） | < 10s / < 30s |
| 批量吞吐 | 40 份论文批处理 | < 2 min |
| LLM 成本 | 每份文档调用成本 | < ¥0.05 |

## 7. 风险与边界

1. **docx 深水区**：样式继承、直接格式覆盖、编号（自动编号 vs 手写编号）、分节、页眉页脚、域代码、图片环绕、表格合并——MVP 只做 P0，复杂项标记"需人工"。
2. **LLM 幻觉**：只允许输出结构化指令；指令执行前校验（段落必须存在、参数在允许范围）；不通过则丢弃并报错。
3. **规范歧义**：部分要求（字间空 2 格、段距"行"换算、网格）不同 Word 版本表现不同，需拿老师的模板实测定容差。
4. **隐私**：真实文档只在本机/私有环境处理；公开仓库不放真实文档、不放学校模板原件；`out/` 需要脱敏。
5. **范围失控**：只服务"毕业论文/设计说明书"一种文档 + 两种 profile；任务书/表格作为第二期（有 doc-templates 可先做回归）。
6. **时间**：与 docling PR 线并行，PR 线每天 ≤10 分钟，别抢主线。
